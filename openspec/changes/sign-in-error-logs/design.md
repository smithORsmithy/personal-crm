# Design

## Context

Зачем это нужно, написано в `proposal.md`, что должно получиться — в `specs/sign-in/spec.md`. Здесь описано, как это сделать.

Что есть сейчас:

- **Очистка для контактов и групп.** `logDbError(context, error)` в `src/db/log-error.ts` пишет в журнал только безопасные поля ошибки. Это тип, текст запроса Drizzle с `$1` вместо значений, код Postgres, имена таблицы, столбца и ограничения, системный код, адрес и порт базы. Так же она проходит по цепочке причин (`cause`, ошибка внутри ошибки). Внутренняя функция `describeError` собирает эти поля, но наружу не видна.
- **Наш код входа уже чистит то, что ловит сам.** `checkSignedInUser` (`src/lib/auth/session-check.ts`) и `requestSignInLink` (`src/lib/auth/sign-in-request.ts`, сбой отправки письма) вызывают `logDbError`.
- **Утечки нашлись в трёх местах.** Проверено на тестовой базе, базу без ответа даёт `withUnreachableDb`.
  1. **Библиотека входа Better Auth пишет в журнал сама.** Её встроенный журнал (logger) печатает ошибку целиком через `console.error`. В ошибке Drizzle (`DrizzleQueryError`) есть поле `params` со значениями запроса, и они же есть в тексте ошибки (`Failed query: … params: …`). Примеры:
     - `getSession` при остановленной базе пишет `INTERNAL_SERVER_ERROR` с ключом сессии в `params`;
     - `signOut` пишет `Failed to read session from database` тоже с ключом сессии.
  2. **Ответы на адреса `/api/auth/*`.** Там открывается ссылка из письма. Ответы собирает библиотека better-call, на которой построен Better Auth. Если ошибка не из числа ошибок самой библиотеки, better-call пишет её `console.error("# SERVER_ERROR: ", error)`, и это никак не настроить. Для ссылки из письма в журнал попадает `magic-link:<ключ ссылки>`. Ещё раньше ту же ошибку пишет журнал Better Auth.
  3. **Ошибки, которые уходят в Next.js.** Next.js сам пишет в журнал ошибку, которая вылетела из страницы, формы (серверного действия) или proxy, со всеми вложенными причинами. Таких мест три:
     - `getCurrentUser` (`src/lib/auth/current-user.ts`) и proxy на страницах (`answerRequest` в `src/lib/auth/proxy-answer.ts`) отпускают дальше ошибку Better Auth, а внутри неё ошибка Drizzle с ключом сессии;
     - `takePlaceInLimit` в `requestSignInLink` отпускает ошибку Drizzle, а в её `params` почта.
- **Как Better Auth даёт вмешаться.** Это проверено на версии 1.7.18:
  - `logger.log(level, message, ...args)` в настройках полностью заменяет его вывод в консоль;
  - `onAPIError.throw: true` не даёт ему и better-call писать неожиданную ошибку `/api/auth/*`: она уходит к тому, кто вызвал `auth.handler`. Ошибки самой библиотеки (отказ, перенаправление) по-прежнему становятся обычными ответами.
- **Текст запроса терялся в собранном приложении.** Это нашлось при проверке собранного приложения с остановленной базой, уже после решений 1–4.
  - `describeError` узнаёт ошибку Drizzle проверкой `error instanceof DrizzleQueryError`.
  - Next.js кладёт свою копию drizzle-orm в несколько частей сборки: страницы, proxy, маршруты. А соединение с базой (`getDb()`) одно на всё приложение, на `globalThis`, и создаёт его та часть, что спросила первой. Обычно это `/health`.
  - Ошибка запроса создаётся классом из той копии, а `describeError` сравнивает с классом из своей. Они не совпадают, поэтому текст запроса пропадает: остаётся `type: 'Error'` и код. Значения при этом тоже не пишутся.
  - Так было на страницах и при выходе. Скорее всего, так же и в журнале контактов и групп на проде.
  - Код ошибки соединения на компьютере владельца — `EACCES` (AggregateError): так отвечает Docker на Windows, когда контейнер базы остановлен. В тестах `withUnreachableDb` и на сервере с Linux — `ECONNREFUSED`.

## Goals / Non-Goals

**Goals:**

- Одни правила очистки для контактов, групп и входа: `describeError` из `src/db/log-error.ts`, без второй копии.
- Ни одна дорога, по которой ошибка входа попадает в журнал, не несёт значения запроса: ни журнал библиотеки, ни ответы `/api/auth/*`, ни ошибки, которые пишет Next.js.
- Проверяется настоящей библиотекой на настоящей тестовой базе: тест смотрит, что на самом деле ушло в консоль.

**Non-Goals:**

- Что видит человек при сбое базы, не меняется (открытый вопрос в `proposal.md`).
- Поля, которые пишутся в журнал контактов, групп, `/health`, скриптов миграций и тестовых данных, не меняются. Меняется только то, как узнаётся ошибка Drizzle (решение 5): в собранном приложении у них возвращается текст запроса.
- Ошибки Next.js, не связанные со входом, этой правкой не трогаются. Когда база остановлена, любая страница падает раньше, на проверке, кто вошёл, а это и есть вход.

## Decisions

### 1. Журнал Better Auth идёт через очистку

`createAuth` передаёт библиотеке `logger: { log: logAuthLibraryMessage }`. Функция живёт в новом файле `src/lib/auth/library-log.ts` и пишет:

- `[Better Auth] <первая строка сообщения>`. Вторая и дальше строки отбрасываются: если библиотека когда-нибудь подставит в сообщение текст ошибки Drizzle, `params:` стоит со второй строки;
- для каждого приложенного объекта-ошибки (`Error`) — `describeError(error)`, то есть те же поля, что у контактов;
- остальные приложенные объекты (не ошибки) не пишутся совсем (решение 4 в `proposal.md`).

Уровни: `error` → `console.error`, `warn` → `console.warn`, остальное → `console.log`. Порог остаётся как у библиотеки по умолчанию: пишутся только `warn` и `error`.

Для этого `describeError` в `src/db/log-error.ts` становится видна другим файлам. Правила очистки не меняются.

Альтернативы:

- выключить журнал библиотеки (`logger.disabled`). Отказ: пропали бы и полезные предупреждения, например о слабом `BETTER_AUTH_SECRET`;
- подменить `console.error` во всём приложении. Отказ: это вмешательство во всё приложение ради одной библиотеки.

### 2. Ошибки `/api/auth/*` отдаются нашему коду

В `createAuth` включается `onAPIError: { throw: true }`. Новая функция `answerAuthRequest(auth, request)` в `src/lib/auth/route-answer.ts` вызывает `auth.handler(request)`. Если вылетела ошибка, она пишет её через `logDbError("Sign-in library request failed", error)` и отвечает `500` без тела, то есть тем же, чем сейчас отвечает better-call. `src/app/api/auth/[...all]/route.ts` вызывает её в `GET` и `POST`. Функция без Next.js, поэтому тесты гоняют её на настоящей библиотеке.

Что видит человек, открывший ссылку при остановленной базе, не меняется: пустая страница браузера с ошибкой 500. Отказы и перенаправления библиотеки, например «Ссылка устарела», не меняются: это её собственные ошибки, они не вылетают наружу.

Альтернатива: свой обработчик `onAPIError.onError`. Отказ: после него better-call всё равно пишет `# SERVER_ERROR` с ошибкой целиком.

### 3. Наружу в Next.js уходит ошибка без данных

Там, где ошибка входа уходила дальше в Next.js, наш код сначала пишет её через `logDbError`, а дальше отпускает новую простую ошибку без причины внутри. Next.js напишет только её текст и место в коде. Мест три:

- **Кто вошёл, для страниц и действий.** Новая `readSignedInUser(auth, headers)` в `src/lib/auth/session-check.ts` возвращает `{ id, email }` или `null`. Если база не ответила, она пишет `Failed to check who is signed in` и отпускает `Error("Could not check who is signed in")`. `getCurrentUser` вызывает её вместо прямого `getSession`. Функция без Next.js, рядом с `checkSignedInUser`, поэтому тесты гоняют её на настоящей библиотеке.
- **Proxy на страницах** (`answerRequest`). Вместо `throw error` он пишет ошибку через `logDbError` и отпускает ту же простую ошибку. Формы, как и сейчас, проходят к своему действию.
- **Подсчёт писем** в `requestSignInLink`. Сбой `takePlaceInLimit` пишется как `Failed to count sign-in emails`, наружу уходит `Error("Could not count sign-in emails")`. Форма, как и сейчас, открывает страницу ошибки.

Альтернатива: `unstable_rethrow` из Next.js, чтобы пропускать служебные ошибки Next.js. Отказ: `session-check.ts` намеренно без Next.js, а `getSession` таких ошибок не бросает. Плагин `nextCookies` ловит свои ошибки сам.

### 4. Тесты смотрят на настоящий вывод в консоль

Новый помощник `captureConsole()` в `test/console.ts` перехватывает `console.error`, `console.warn` и `console.log` и собирает то, что Node напечатал бы в журнал. Это `util.inspect` каждого аргумента, как его печатает `console`. Ошибку, которая вылетела наружу, тест прогоняет через тот же `util.inspect`: так её напечатает Next.js.

Каждый тест сценария проверяет две вещи:

- **значений нет:** ни `params:`, ни ключа сессии (часть cookie `better-auth.session_token` до точки), ни ключа из ссылки, ни почты;
- **полезное есть:** текст запроса к нужной таблице с `$1` и `ECONNREFUSED` (база без ответа в тестах даёт этот код).

Сначала каждый тест красный: сейчас библиотека и Next.js печатают значения.

У сценария «Запросить ссылку при остановленной базе» два теста:

- **База не отвечает.** Почта сейчас в журнал и так не попадает: соединение рвётся до первого запроса, а у ошибки соединения нет значений. Тест закрепляет, что так и останется.
- **Запрос к базе упал, когда база отвечает.** Внутри откатываемой транзакции тест удаляет таблицу `sign_in_emails`, и запрос подсчёта падает. Тогда почта есть в `params`, и тест сначала красный.

e2e не добавляются: остановить базу в e2e нельзя, не помешав остальным тестам. Так же, через `withUnreachableDb`, проверялись прежние сценарии «База данных недоступна». Существующие e2e входа и главного сценария проверяют, что `/api/auth/*` и `getCurrentUser` работают как раньше.

Ручная проверка и проверка агентом идут в собранном приложении, а не в `pnpm dev`. Режим разработки сам пишет в терминал каждую строку запроса с адресом целиком, а в адресе ссылки из письма есть её ключ. Собранное приложение, как и на сервере, строк запросов не пишет. Это поведение Next.js в режиме разработки, на сервер оно не попадает.

Тесты Vitest не видят, как Next.js раскладывает код по частям сборки. Поэтому агент ещё раз проходит четыре сценария в собранном приложении (на базе e2e, с остановленным контейнером Postgres) и смотрит его журнал. Так нашлась потеря текста запроса (решение 5).

### 5. Ошибка Drizzle узнаётся по полям, а не по классу

Решение владельца. `describeError` считает ошибку ошибкой запроса Drizzle, если она его класса (как сейчас) или если у неё есть поле `query` (строка) и поле `params` (список). Это поля, которые задаёт конструктор `DrizzleQueryError` в drizzle-orm. Из такой ошибки, как и раньше, берётся только `query`, а `params` не пишется.

Ошибка postgres.js (`PostgresError`) тоже несёт текст запроса, но её значения лежат в поле `parameters`, а не `params`. Поэтому по этому правилу она не узнаётся и остаётся как сейчас: из неё пишутся только безопасные поля.

Тест в новом `src/db/log-error.test.ts`: ошибка с полями Drizzle, но не его класса, — как из другой части сборки. В журнале должен быть текст запроса с `$1`, а значений из `params` и текста `params:` быть не должно. Ошибка без `params` текст запроса не отдаёт.

Альтернативы:

- одна копия drizzle-orm на всю сборку (`serverExternalPackages` в `next.config.ts`). Отказ: это меняет сборку и образ ради журнала, а копия соединения на `globalThis` всё равно может прийти из другой части;
- сравнивать имя класса (`constructor.name`). Отказ: при сжатии кода сборкой имена классов могут меняться.

## Risks / Trade-offs

- [Новая версия Better Auth начнёт писать ошибки по-другому или в другом месте] → тесты работают с настоящей библиотекой и смотрят на настоящий вывод в консоль. Значение в журнале сделает их красными.
- [Библиотека подставит значение запроса прямо в текст сообщения, в первую строку] → сейчас так делает только отказ подозрительному запросу: в журнал попадает адрес сайта, откуда он пришёл (решение 3 в `proposal.md`). Ключа сессии и почты библиотека в тексты сообщений не вставляет.
- [`readSignedInUser` ловит любую ошибку и может спрятать служебную ошибку Next.js] → `getSession` не вызывает Next.js, кроме плагина `nextCookies`, а тот ловит свои ошибки сам. Все страницы проходят e2e в CI.
- [`onAPIError.throw` меняет, как отвечают `/api/auth/*`] → меняется только неожиданная ошибка: раньше 500 отдавала библиотека, теперь наш код. Вход по ссылке, «Ссылка устарела» и выход проверяют существующие тесты и e2e.
- [Меньше подробностей при разборе сбоя] → остаются текст запроса, коды и адрес базы, как у контактов. По ним видно, какой запрос и почему не прошёл.
- [Одна ошибка — две строки в журнале: библиотеки и наша] → обе без значений. Строка библиотеки говорит, где упало внутри неё, наша — что делал вход.
- [Чужая ошибка с полями `query` и `params` примет за текст запроса что-то со значениями] → такие поля задаёт только drizzle-orm, а он всегда передаёт значения отдельно, в `params`, а в тексте ставит `$1`. В проекте запросы пишутся шаблоном `sql\`…\`` или построителем Drizzle, значения туда не вклеиваются.
- [Новая версия drizzle-orm переименует поля] → тест решения 5 на настоящей ошибке не упадёт, но текст запроса пропадёт из журнала. Значения при этом не появятся: пишутся только перечисленные поля.

## Migration Plan

База данных не меняется, миграций нет, существующие данные не трогаются. Выкатка обычная: merge в main → образ → сервер. Откатиться можно, запустив предыдущий образ: данных эта правка не касается.
