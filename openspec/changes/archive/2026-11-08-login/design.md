# Design

## Context

Зачем и что меняется — `proposal.md`, требования — `specs/sign-in`, `specs/data-ownership`, `specs/contact-groups` этого изменения.

Как устроено сейчас (то, от чего отталкивается решение):

- **Пользователей нет.** Все запросы к базе отдают все данные. Доступ к данным разложен на два слоя: функции, которые принимают базу параметром и ничего не знают про Next.js (`src/lib/contacts/list.ts`, `due.ts`, `commands.ts`, `save.ts`, `src/lib/groups/store.ts`, `commands.ts`), — их проверяют тесты Vitest на настоящей тестовой базе; и тонкий слой Next.js над ними — `queries.ts` (чтение для страниц) и `actions.ts` (серверные действия — функции, которые браузер вызывает при отправке формы).
- **Next.js 16 с `cacheComponents: true`.** Всё, что читает запрос (cookie, заголовки, базу), должно сидеть внутри `<Suspense>`; страницы уже так устроены — каждая читает данные в своих блоках внутри `<Suspense>` после `await connection()`. Общих кешей между запросами (`use cache`) в коде нет. Вместо `middleware.ts` в Next.js 16 — `proxy.ts`: код, который выполняется до страницы на каждый запрос, по умолчанию в среде Node.js (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`, `.../02-guides/authentication-with-cache-components.md`).
- **База:** таблицы `contacts`, `notes`, `groups`, `contact_groups`. Пять начальных групп вставляет миграция `0004_groups_presets.sql`, поэтому они есть в любой новой базе, в том числе в тестовых. Название группы уникально на всю базу (`groups_name_lower_idx`).
- **Миграции:** на сервере — разовый контейнер `migrate` из нового образа (`scripts/migrate.ts`); локально `pnpm db:migrate` — это `drizzle-kit migrate`; тестовые базы пересоздаёт `test/recreate-db.ts`. Drizzle применяет все новые миграции **в одной транзакции**: упала одна — откатываются все, база остаётся как была (проверено по `drizzle-orm/pg-core/dialect.js`).
- **Выкатка:** `deploy/deploy.sh`: бэкап базы → миграции → новый образ → `/health`. Настройки сервера — в `/srv/crm/.env`, его подставляет `deploy/compose.yaml`. nginx перед приложением ставит заголовок `X-Real-IP` с настоящим адресом посетителя.
- **e2e (Playwright):** собранное приложение на порту 3100 со своей пустой базой `<имя>_e2e_test`; `e2e/db.ts` кладёт стартовые данные прямо в базу. Тесты «в другом браузере» открывают новый контекст браузера без общих cookie.
- **Версии на сегодня:** `better-auth` 1.7.18, `nodemailer` 10.3.1 (типы внутри пакета, `@types/nodemailer` не нужен), образ Mailpit `axllent/mailpit:v1.33`. При реализации — проверить ещё раз и взять последние стабильные.

## Goals / Non-Goals

**Goals:**

- Владелец записи определяется только на сервере, по сессии; номер пользователя никогда не приходит из браузера.
- Изоляцию данных проверяют тесты на каждую функцию доступа к данным, а не только интерфейс.
- Существующие данные переходят к владельцу одной миграцией, атомарно: либо всё, либо ничего.
- Одна сборка образа: куда слать письма, какой адрес сайта и чья почта владельца — только настройки.

**Non-Goals:**

- Защита на уровне базы (row-level security в Postgres) — права проверяет код приложения.
- Чистка старых сессий и неиспользованных ссылок по расписанию — строк мало, библиотека удаляет просроченное, когда натыкается на него.
- Возврат после входа на страницу, которую открывали до входа (решение 4 в `proposal.md`).

## Decisions

### 1. Better Auth: как настроен

Библиотека входа Better Auth с плагином `magicLink` (вход по ссылке из письма) и адаптером Drizzle. Настройки:

- `magicLink({ expiresIn: 900, sendMagicLink })` — ссылка живёт 15 минут. Одноразовость встроена: плагин атомарно удаляет ссылку при первом открытии (`consumeVerificationValue`). Новый пользователь создаётся при первом открытии ссылки, имя — пустая строка (решение 10 в `proposal.md`).
- `session: { expiresIn: 30 дней, updateAge: 1 день }` — сессия (запись «это устройство вошло как такой-то пользователь») живёт 30 дней и продлевается на 30 дней от текущего момента, если с прошлого продления прошли сутки. Отсюда «от 29 до 30 дней с последнего захода» (решение 8 в `proposal.md`).
- Таблицы во множественном числе, как остальные в проекте: `drizzleAdapter(db, { provider: "pg", schema, usePlural: true })` → `users`, `sessions`, `accounts`, `verifications`. Номера пользователей — строки, как по умолчанию в Better Auth (`text`): так меньше настроек и сюрпризов.
- `disabledPaths: ["/sign-in/magic-link"]` — запросить ссылку напрямую через адрес `/api/auth/sign-in/magic-link` нельзя (404). Единственный вход — серверное действие формы входа (решение 3). Так проверка почты, лимит и отмена старых ссылок живут в одном месте, и их нельзя обойти. Серверный вызов `auth.api.signInMagicLink` при этом работает: `disabledPaths` проверяется только для запросов из сети.
- `advanced.ipAddress.ipAddressHeaders: ["x-real-ip"]` — встроенный лимит Better Auth (5 открытий ссылки в минуту с одного адреса) считает по адресу, который ставит nginx. Без этого лимит считал бы всех посетителей одним адресом.
- `telemetry: { enabled: false }`, `baseURL` и `secret` — из настроек (решение 10).
- Плагин `nextCookies()` последним — чтобы серверные действия (выход) могли ставить и стирать cookie.

Код: `src/lib/auth/create-auth.ts` — функция `createAuth({ db, mailer, from, baseURL, secret, plugins })` без Next.js: тесты собирают её на тестовой базе. `src/lib/auth/index.ts` (`server-only`) — `getAuth()`, которая собирает экземпляр при первом вызове из `getDb()` и настроек, как `getDb()` сейчас: `next build` загружает файлы, но настроек при сборке нет. Обработчик `src/app/api/auth/[...all]/route.ts` вызывает `getAuth().handler(request)` внутри функций `GET`/`POST`, а не на верхнем уровне файла.

Почему не Auth.js, Lucia и т. п.: Better Auth задан спекой. Почему не свой код сессий: одноразовые ссылки, подписанные cookie и продление — ровно то, что делает библиотека, и там легко ошибиться.

### 2. Таблицы и владелец

- `users`, `sessions`, `accounts`, `verifications` — схема ядра Better Auth той версии, что ставим; описываются в `src/db/schema.ts` по его документации (сверить с генератором схемы Better Auth). `accounts` для входа по ссылке не используется, но входит в обязательную схему. `sessions.user_id` и `accounts.user_id` → `users.id` с `ON DELETE CASCADE`, как у Better Auth.
- `sign_in_emails` — отправленные письма для лимита: `id` (identity), `email` (`text`, уже приведённая к маленьким буквам), `sent_at` (`timestamptz`, по часам базы), индекс `(email, sent_at)`.
- `contacts.owner_id` и `groups.owner_id` — `text NOT NULL`, ссылка на `users.id` **без** каскадного удаления: удалить пользователя, у которого есть данные, база не даст. Удаления аккаунта в продукте нет, так случайно не потеряем контакты.
- Индекс `contacts (owner_id)` — список контактов всегда читается по владельцу.
- Уникальность названия группы — в пределах владельца: индекс `groups_name_lower_idx` заменяется на `groups_owner_id_name_lower_idx` по `(owner_id, lower(name)) WHERE deleted_at IS NULL`.
- У `notes` и `contact_groups` своего владельца нет: заметка принадлежит владельцу контакта, связь «контакт — группа» создаётся только между записями одного владельца (решение 7).

Альтернатива — `owner_id` и в `contact_groups` с составными внешними ключами `(contact_id, owner_id)` и `(group_id, owner_id)`: тогда связать чужие записи не даст сама база. Отклонено: заметно усложняет схему и миграцию; та же гарантия даётся проверкой в коде, и её проверяют тесты.

### 3. Запрос ссылки: одна функция и серверное действие

`src/lib/auth/sign-in-request.ts` — `requestSignInLink(db, auth, rawEmail, headers)`, без Next.js, проверяется тестами на тестовой базе. Шаги:

1. **Почта:** `normalizeEmail` (`src/lib/auth/email.ts`) — убрать пробелы по краям, привести к маленьким буквам, проверить схемой `z.email()` (та же, что внутри Better Auth). Неверная → результат `invalid`, письма нет.
2. **Лимит:** в транзакции берётся блокировка на эту почту (`pg_advisory_xact_lock(hashtext(email))` — два одновременных запроса одной почты идут по очереди), считаются строки `sign_in_emails` этой почты за последние 10 минут по часам базы. Уже 3 → результат `too-many`. Иначе — вставить строку (место в лимите занято) и заодно удалить строки старше 10 минут, чтобы таблица не росла.
3. **Ссылка:** `auth.api.signInMagicLink({ body: { email, callbackURL: "/", newUserCallbackURL: "/", errorCallbackURL: "/login/link-expired" }, headers })`. Better Auth создаёт ссылку и вызывает `sendMagicLink` (решение 4).
4. **Ошибка отправки** (почтовый сервер не ответил) → строка лимита удаляется (лимит считает только отправленные письма — решение 3 в `proposal.md`), результат `failed`.

Серверное действие `src/lib/auth/actions.ts` → `requestSignInLinkAction` превращает результат в состояние формы: `sent` → «Ссылка для входа отправлена на <почта>», `invalid` → ошибка у поля «Проверьте адрес почты» (вписанный текст возвращается в поле), `too-many` → «Слишком часто, попробуйте через несколько минут», `failed` → «Не получилось отправить письмо. Попробуйте ещё раз через минуту» — этого текста нет в спеке, он нужен на случай сбоя почты; показать владельцу. Ответ одинаковый для новой и знакомой почты: функция вообще не смотрит, есть ли пользователь.

### 4. Письма: Nodemailer и одна настройка `SMTP_URL`

`src/lib/auth/mail.ts`:

- `createMailer(smtpUrl)` — транспорт Nodemailer из строки подключения: локально и в CI `smtp://127.0.0.1:1025` (Mailpit), на сервере `smtps://resend:<ключ Resend>@smtp.resend.com:465` (Resend принимает письма по протоколу SMTP: логин `resend`, пароль — ключ). Пакет Resend для Node.js не нужен — меньше зависимостей, и код одинаковый везде.
- `buildSignInEmail({ to, url, from })` — письмо: отправитель из настройки `MAIL_FROM` (`"Личная CRM" <noreply@mail.crm.linkbook.site>`), тема «Вход в Личную CRM», HTML с кнопкой «Войти» и текстовая версия с той же ссылкой; срок 15 минут и строка «Если вы не запрашивали вход — просто проигнорируйте письмо». Почтовые программы не понимают CSS-переменные, поэтому цвета и отступы письма — значения тех же дизайн-токенов из `src/styles/tokens.css`, записанные прямо в письме, в одном месте с комментарием, откуда они.
- `sendMagicLink({ email, url, token })` в `createAuth`: сначала удаляет все прежние ссылки этой почты (`DELETE FROM verifications WHERE identifier LIKE 'magic-link:%' AND identifier <> 'magic-link:' || token AND value::jsonb ->> 'email' = email`), потом отправляет письмо. Формат записи (`magic-link:<токен>`, почта в JSON поля `value`) — внутреннее устройство плагина 1.7 (`dist/plugins/magic-link/index.mjs`); тест «новая ссылка отменяет прежние» упадёт, если оно поменяется при обновлении библиотеки.

В тестах Vitest — встроенный транспорт Nodemailer `jsonTransport`: письмо собирается целиком, но никуда не уходит, тест читает его поля. Это настоящий Nodemailer, не подделка. В e2e — Mailpit (решение 11).

### 5. Ссылка из письма и «Ссылка устарела»

Ссылка ведёт на `/api/auth/magic-link/verify?token=…&callbackURL=/&errorCallbackURL=/login/link-expired`. Успех — Better Auth ставит cookie сессии и открывает `/`. Ссылка использована, просрочена или отменена — открывается `/login/link-expired?error=…`: статичная страница «Ссылка устарела, запросите новую» с кнопкой-ссылкой «На страницу входа» (`/login`); код ошибки не показывается — все случаи выглядят одинаково (решение 7 в `proposal.md`).

### 6. Кто вошёл: proxy, проверка в каждой странице и действии, шапка

- **`src/proxy.ts`** — на каждый запрос, кроме `/api/auth/*`, `/health`, `/login/link-expired` и статики (`_next/static`, `_next/image`, файлы с расширением), спрашивает Better Auth о сессии (`auth.api.getSession({ headers, returnHeaders: true })`, один запрос к базе). Нет сессии — перенаправляет на `/login` (сам `/login` пропускает). Есть сессия и открыт `/login` — перенаправляет на `/`. Если Better Auth продлил сессию, proxy передаёт браузеру обновлённую cookie (`Set-Cookie`) — без этого продлевалась бы только запись в базе, а cookie в браузере истекла бы через 30 дней после входа: страницы (серверные компоненты) ставить cookie не могут, а `nextCookies()` при отрисовке страниц продление пропускает.
- **Проверка не только в proxy.** Next.js прямо предупреждает: proxy — первый фильтр, а не защита данных. Поэтому `src/lib/auth/current-user.ts` (`server-only`): `getCurrentUser()` — сессия из `headers()`, обёрнута в `cache()` из React (один раз за запрос), возвращает только `{ id, email }`; `requireUserId()` — то же, но без сессии делает `redirect("/login")`. Каждая функция в `queries.ts` и каждое серверное действие в `actions.ts` первым делом вызывает `requireUserId()`. Номер пользователя из браузера не принимается нигде.
- **Шапка:** в `src/app/layout.tsx` справа от логотипа — `<Suspense fallback={null}><UserMenu /></Suspense>`. `UserMenu` (`src/components/user-menu.tsx`) читает `getCurrentUser()`: нет пользователя (страница входа) — ничего не рисует; есть — почта (на узком экране обрезается многоточием) и кнопка «Выйти». Кнопка — клиентский компонент `src/components/sign-out-button.tsx`: открывает окошко подтверждения — готовый `AlertDialog` из shadcn/ui, как у удаления контакта (`delete-contact-button.tsx`), с заголовком «Вы уверены?» и кнопками «Нет, вернуться» (`AlertDialogCancel`: закрывает окошко, на сервер ничего не уходит; так же закрывает Esc) и «Да, выйти» (форма с серверным действием `signOut`: `auth.api.signOut({ headers })` удаляет только текущую сессию, `nextCookies()` стирает cookie, затем `redirect("/login")`).
- **Страница входа** `src/app/login/page.tsx` + клиентская форма `src/components/sign-in-form.tsx` на `useActionState`, из готовых компонентов shadcn/ui (поле, кнопка, карточка), как остальные формы.

### 7. Свои данные в коде

Правило: функции, которые принимают базу, получают ещё и `ownerId` и сами ограничивают каждый запрос владельцем; слой Next.js берёт `ownerId` только из `requireUserId()`.

- **Контакты:** `selectContactList(db, ownerId)`, `getContact`, `listNotes` (через владельца контакта), `getRecentlyDeletedContact` (иначе по `/?deleted=<номер>` чужой увидел бы имя — сценарий «Сообщение об удалении чужого контакта»), `createContactWithGroups` (пишет `owner_id`), `updateContactWithGroups`, удаление, возврат, заметка, частота, своя дата — во всех `WHERE` добавляется `owner_id = $ownerId`. Чужая запись даёт тот же ответ, что и несуществующая: «Контакт не найден…», а удаление молча открывает список (как сейчас для контакта, удалённого в другом браузере).
- **«Пора связаться»:** `selectDueContacts`, `countDueContacts`, `hasContactsWithFrequency` (`due.ts`) — условие по владельцу.
- **Группы:** все функции `store.ts` — по владельцу: список с числом людей, группы контакта, поиск по названию, создание (с `owner_id`), переименование, удаление и возврат, членство. Добавить в группу можно только если и контакт, и группа принадлежат `ownerId`; чужие номера групп в форме контакта считаются исчезнувшими группами. `findOrCreateGroup` ищет и создаёт группу владельца.
- **Фильтр `/?group=`:** уже сверяется со списком групп пользователя — чужой номер даёт «Все».
- **Окончательное удаление** контактов и групп после 5 секунд (`eraseDeletedContacts`, `eraseExpiredGroups`) остаётся общим: оно трогает только записи, помеченные удалёнными, чьи бы они ни были.
- **«Контакт не найден»:** `src/app/contacts/[id]/not-found.tsx` — заголовок «Контакт не найден» и кнопка «К списку контактов»; срабатывает и для страницы «Изменить» (решение 9 в `proposal.md`). Общая `src/app/not-found.tsx` остаётся для прочих адресов.

### 8. Существующие данные: три миграции и `OWNER_EMAIL`

Миграция в SQL не может прочитать переменную окружения. Поэтому запускающий миграции скрипт кладёт почту владельца в настройку сеанса Postgres, а миграция читает её оттуда:

- `scripts/migrate.ts` читает `OWNER_EMAIL`, проверяет её той же `normalizeEmail` (неверная → ошибка до любых изменений: иначе данные достались бы почте, под которой нельзя войти) и выполняет `select set_config('crm.owner_email', <почта>, false)` на том же единственном соединении (`max: 1`), на котором затем идут миграции.
- `pnpm db:migrate` переходит с `drizzle-kit migrate` на `tsx scripts/migrate.ts` — один и тот же путь локально и на сервере. `test/recreate-db.ts` делает то же с тестовой почтой владельца `owner@example.test`.

Миграции (Drizzle сам кладёт их в `drizzle/`):

1. **`0005_users` — сгенерированная** (`pnpm db:generate`): таблицы `users`, `sessions`, `accounts`, `verifications`, `sign_in_emails`; столбцы `owner_id` у `contacts` и `groups` — пока **без** `NOT NULL`; внешние ключи и индекс `contacts (owner_id)`. Существующие данные не меняет.
2. **`0006_owner_data` — написанная руками** (`drizzle-kit generate --custom`): блок `DO $$ … $$`:
   - берёт `current_setting('crm.owner_email', true)`;
   - почты нет: если в `contacts` или `groups` есть строки — `RAISE EXCEPTION 'OWNER_EMAIL is not set: existing contacts and groups need an owner'`, иначе ничего не делает;
   - почта есть: создаёт пользователя с этой почтой (`email_verified = true`, пустое имя, `id = gen_random_uuid()::text`), если такого ещё нет, и ставит его `owner_id` всем контактам и группам, у которых владельца нет. Заметки и связи с группами не трогает — они следуют за контактами.
3. **`0007_owner_required` — сгенерированная** после `.notNull()` в схеме: `owner_id SET NOT NULL` у обеих таблиц; замена индекса уникальности названия группы (решение 2).

Что с данными: ни одна строка не удаляется и не добавляется, кроме одной строки в `users`; меняется только новый столбец `owner_id`. Все три миграции идут в одной транзакции (Context): упала любая — база остаётся как до выкатки, контейнер миграций завершается с ошибкой, новый образ не стартует. Пять начальных групп из `0004` есть в любой базе, поэтому на практике `OWNER_EMAIL` нужна всегда, в том числе в тестовых базах.

Когда владелец впервые входит по ссылке, Better Auth находит уже созданного пользователя по почте (поиск без учёта больших букв) — и владелец видит свои данные.

Проверка миграции — отдельный тест на своей базе `<имя>_migration_test`: применить миграции до `0004`, положить контакты, заметки, группы и связи, применить остальные с почтой владельца → число строк в каждой таблице прежнее, у всех строк `owner_id` владельца; без почты → ошибка, база на шаге `0004`, данные прежние. Миграцию `0006` показать владельцу до merge (CLAUDE.md).

### 9. Тестовые данные у владельца

`scripts/seed.ts` требует `OWNER_EMAIL`: находит пользователя с этой почтой или создаёт его — тем же способом, что миграция `0006`. «Пустая база» теперь значит «у владельца нет контактов». Контакты создаются с его `owner_id`, раскладываются по его группам с начальными названиями; `scripts/seed-groups.ts` смотрит только контакты и группы владельца. `deploy/seed.sh` передаёт `OWNER_EMAIL` в контейнер (через `deploy/compose.yaml`, решение 12).

### 10. Настройки

| Настройка | Зачем | Компьютер (`.env`) | CI | Сервер |
| --- | --- | --- | --- | --- |
| `BETTER_AUTH_SECRET` | подпись cookie сессий, секрет | случайная строка | одноразовое значение в workflow | `/srv/crm/.env` |
| `BETTER_AUTH_URL` | адрес сайта для ссылок в письмах | `http://localhost:3000` | `http://127.0.0.1:3100` (ставит `e2e/start-app.ts`) | `https://app.linkbook.site` в `deploy/compose.yaml` |
| `SMTP_URL` | куда отдавать письма | `smtp://127.0.0.1:1025` | `smtp://127.0.0.1:1025` | `/srv/crm/.env`, с ключом Resend — секрет |
| `MAIL_FROM` | отправитель | `"Личная CRM" <noreply@mail.crm.linkbook.site>` | то же | то же, в `deploy/compose.yaml` |
| `OWNER_EMAIL` | чьи старые данные и тестовые данные | своя почта | не нужна: тестовые базы получают `owner@example.test` прямо из `test/recreate-db.ts` | `/srv/crm/.env` |

`.env` агент не читает и не пишет: владелец добавляет строки сам, агент говорит какие; в `.env.example` — те же имена без значений. Приложение при первом обращении к входу проверяет, что настройки есть, и падает с понятной ошибкой без значений («BETTER_AUTH_SECRET is not set»). Адрес сайта: локально открывать именно `http://localhost:3000` — cookie привязана к адресу из `BETTER_AUTH_URL` (записать в README).

### 11. Тесты

TDD, как в CLAUDE.md: тест → красный → код → зелёный. Каждый сценарий спеки — свой тест; название теста — название сценария.

**Vitest на тестовой базе:**

- `email.test.ts` — нормализация и проверка почты.
- `sign-in-request.test.ts` — экземпляр `createAuth` на тестовой базе и `jsonTransport`: письмо уходит и содержит ссылку; почта с пробелами и большими буквами; неверная почта — письма нет; одинаковый ответ для новой и знакомой почты; 4-е письмо за 10 минут — `too-many` (старые строки «состариваются» сдвигом `sent_at` в базе); через 10 минут снова можно; другая почта не затронута; новая ссылка отменяет прежние; ссылка живёт 15 минут (`expires_at` − время создания); ошибка отправки не занимает место в лимите (транспорт на порт, где никто не слушает, — настоящая ошибка соединения, как `withUnreachableDb`).
- `mail.test.ts` — поля письма: отправитель, тема, «Войти», 15 минут, строка про «не запрашивали».
- `session.test.ts` — сессия старше суток продлевается до «сейчас + 30 дней», ответ ставит cookie на 30 дней; просроченная сессия — пользователя нет; выход удаляет только свою сессию.
- Существующие тесты контактов, групп и «Пора связаться» получают владельца (`test/fixtures.ts`: `addUser(db, email)`, `addContact(db, ownerId, …)`), плюс на **каждую** функцию доступа к данным тест «чужая запись — как будто её нет, данные не изменились».
- Тест миграции существующих данных (решение 8) и тесты `seed` у владельца.

**e2e (Playwright):**

- `e2e/mailpit.ts` — чтение писем через API Mailpit (`/api/v1/search?query=to:"…"`, `/api/v1/message/<id>`), ожидание нового письма, ссылка из кнопки «Войти». Адрес Mailpit — `MAILPIT_URL`, по умолчанию `http://127.0.0.1:8025`.
- `e2e/auth.ts` — `signIn(page, email)`: страница входа → почта → «Получить ссылку» → ссылка из Mailpit → внутри. Почты уникальны для каждого теста (`a-<случайное>@example.test`), чтобы лимит 3 письма и письма других тестов не мешали.
- Каждый контекст браузера получает свой заголовок `X-Real-IP` (`extraHTTPHeaders`) — то, что на сервере ставит nginx: тесты, как разные посетители, не упираются во встроенный лимит 5 открытий ссылки в минуту с одного адреса.
- `e2e/sign-in.spec.ts` — критерий успеха спеки (A добавил контакт; B не видит его ни в списке, ни в поиске, по прямой ссылке — «Контакт не найден») и остальные сценарии `sign-in` и `data-ownership`, которые видны в браузере. Просроченная ссылка — сдвиг `expires_at` в e2e-базе через `e2e/db.ts`; «запрос не из формы» — прямой запрос на `/api/auth/sign-in/magic-link` (404) и проверка, что письма нет.
- `e2e/main-scenario.spec.ts` и `e2e/keep-in-touch.spec.ts` остаются отдельными от теста входа: перед сценарием входят под новым пользователем; «другой браузер» входит под той же почтой своей ссылкой. `e2e/db.ts` кладёт контакты и группы для пользователя по его почте (пользователь уже создан входом).

### 12. Docker, CI, выкатка

- `compose.yaml` (локально): сервис `mailpit` (`axllent/mailpit`, порты `127.0.0.1:1025` — приём писем и `127.0.0.1:8025` — страница), без хранения писем между перезапусками.
- `.github/workflows/ci.yml`: в задаче e2e — сервис Mailpit и переменные `BETTER_AUTH_SECRET` (одноразовая, как `POSTGRES_PASSWORD: ci-only`), `SMTP_URL`, `MAIL_FROM`. Задаче unit-тестов нового не нужно: тесты передают `createAuth` тестовый секрет и транспорт сами.
- `deploy/compose.yaml`: приложению — `BETTER_AUTH_SECRET`, `SMTP_URL` (обязательные, `${…:?…}`), `BETTER_AUTH_URL`, `MAIL_FROM`; контейнеру `migrate` — `OWNER_EMAIL` (обязательная). Docker compose проверяет обязательные настройки при любой команде, поэтому без них `deploy.sh` останавливается на первом же шаге — до бэкапа и миграций, старая версия работает (сценарий «Настройки OWNER_EMAIL нет»).
- `Dockerfile` не меняется: `scripts/migrate.ts` и `seed.ts` по-прежнему собираются esbuild в отдельные файлы.
- README: вход, Mailpit, новые строки `.env` локально и на сервере, Resend, откат «база + версия вместе».

## Risks / Trade-offs

- [Почтовые программы и антивирусы иногда сами открывают ссылки из писем для проверки — одноразовая ссылка сгорит до того, как человек нажмёт] → С Gmail и обычными ящиками так не бывает; если случится — промежуточная страница с кнопкой «Войти» (отдельная доработка, с согласия владельца).
- [Хостинг сервера закрывает исходящие почтовые порты 465/587] → До выкатки проверить с сервера соединение со `smtp.resend.com:465`; закрыт — Resend принимает и на порт 2465 (меняется только `SMTP_URL`).
- [Письма попадают в спам, пока домен не подтверждён] → Подтвердить `mail.crm.linkbook.site` в Resend записями DNS (SPF, DKIM) до выкатки; проверить письмо на настоящий ящик сразу после выкатки.
- [Отмена прежних ссылок опирается на внутренний формат записей Better Auth] → Тест «новая ссылка отменяет прежние»; при обновлении библиотеки он покажет, если формат изменился.
- [Better Auth в транзакции-откатке Vitest (`withRollback`) может вести себя иначе, чем на обычном соединении] → Если адаптер не работает с транзакцией, тесты входа чистят свои строки сами (уникальные почты, удаление в `afterEach`).
- [proxy делает запрос к базе на каждый запрос, плюс проверка в странице] → Два коротких запроса по индексу; при нынешнем числе пользователей незаметно. Если станет заметно — кеш сессии Better Auth в cookie.
- [proxy собирается отдельно от страниц и открывает своё соединение с базой] → Пул небольшой; число соединений Postgres по умолчанию (100) с запасом.
- [Next.js с Cache Components может предупреждать о страницах, которые читают сессию] → Чтение сессии сидит в тех же блоках `<Suspense>`, что и чтение базы; если сборка требует — `export const instant = false` на таких страницах, как советует руководство Next.js.
- [Пока владелец не добавил `OWNER_EMAIL` и остальные строки в `.env` сервера, выкатка красная] → Это и есть защита; порядок шагов — в Migration Plan и в `tasks.md`.
- [Встроенный лимит Better Auth на один адрес: в одной квартире за одним роутером 5 открытий ссылок в минуту на всех] → Для нескольких друзей не достижимо; при нужде лимит настраивается.
- [Владелец ещё не входил, а данные уже его] → Ничего не теряется: данные ждут первого входа под `OWNER_EMAIL`.

## Migration Plan

**До merge (только человек):**

1. Завести аккаунт Resend, добавить домен `mail.crm.linkbook.site`, внести записи DNS, которые покажет Resend, дождаться «Verified»; создать ключ с правом только отправки.
2. Добавить в `/srv/crm/.env` (права 600 сохраняются) строки `OWNER_EMAIL`, `BETTER_AUTH_SECRET`, `SMTP_URL` — агент даст точный вид строк и команду для секрета.
3. Агент проверяет с сервера доступность `smtp.resend.com:465` и показывает владельцу миграцию `0006`.

**Выкатка:** merge → обычный `deploy.sh`: бэкап (файл с номером прошлой версии) → три миграции одной транзакцией → новый образ → `/health`. Затем вручную: войти под `OWNER_EMAIL` → число контактов на главной и группы с числами людей как до выкатки, заметки в карточках на месте; войти под другой почтой → пусто; письмо пришло в настоящий ящик.

**Откат — только вместе, база и версия, запускает владелец:**

1. Сначала `restore.sh` с бэкапом, снятым перед выкаткой (в имени — номер прошлой версии). Скрипт предупредит `WARNING`, что версии бэкапа и приложения разные, — здесь это ожидаемо, ответить `yes`. Порядок именно такой: если сначала откатить приложение, старая версия без входа на несколько минут показала бы всем все данные, в том числе контакты друзей.
2. Затем Actions → Deploy → `image_tag` = номер прошлой версии.

Всё, что пользователи добавили после выкатки, при откате пропадёт — бэкап снят до неё. README получает этот порядок.
