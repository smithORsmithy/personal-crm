# Design

## Context

Зачем фича — в `proposal.md`, что именно должно работать — в `specs/keep-in-touch/spec.md`. Здесь — как это устроить в текущем коде.

Макеты экранов для телефона и компьютера: [Макеты экранов keep-in-touch](https://claude.ai/artifact/Uvmk6uakFZzq1fWavpxXbY). Экраны делаются по ним. Если макет расходится с требованиями, правы требования. Имена, телефоны и заметки на макетах выдуманы.

Что есть сейчас:

- Таблица `contacts` (поля контакта, `created_at`, `deleted_at` для удаления с отменой) и таблица `notes` (`contact_id`, `body`, `created_at`). У заметок уже есть индекс `notes_contact_id_created_at_idx` по контакту и дате, новые сверху — по нему быстро находится последняя заметка контакта.
- Все чтения — в `src/lib/contacts/queries.ts`, все изменения — серверные действия (server actions — функции, которые браузер вызывает, а выполняются они на сервере) в `src/lib/contacts/actions.ts`. Страницы читают данные на каждый запрос (`connection()`), поэтому любое изменение видно сразу и во всех браузерах.
- Время уже сейчас считается по часам базы данных (`now()`): так сделано для окна отмены удаления. Даты заметок ставит тоже база.
- Тестов и библиотеки для тестов в проекте нет; проверка — `pnpm lint`, `pnpm typecheck`, `pnpm build` и ручные сценарии.
- Среди компонентов `src/components/ui/` нет выпадающего списка и нет окошка с полем ввода: есть только `alert-dialog` для подтверждения удаления.

## Goals / Non-Goals

**Goals:**

- Одно правило «пора связаться» в одном месте кода: страница и число на кнопке главной всегда совпадают.
- Срок считается в момент чтения из уже хранимых данных, без отдельного «следующего срока», который нужно не забывать обновлять.
- Миграция только добавляет необязательные поля: старая версия приложения продолжает работать, пока стартует новая.

**Non-Goals:**

- Фоновые задачи, расписания и уведомления — не нужны: список строится при открытии страницы.
- Часовой пояс пользователя: даты считаются и показываются так же, как сейчас в карточке (по часам сервера).
- Тестовая библиотека: её добавление — отдельное решение владельца.

## Decisions

### 1. Частота — отдельный тип в базе, своя дата — два поля рядом

Новое необязательное поле `contacts.contact_frequency` типа `contact_frequency` (перечисление PostgreSQL — тип, который принимает только заранее заданные значения): `weekly`, `monthly`, `quarterly`, `yearly` и `on_date` для «Другое». Пусто (`null`) — «Не задано».

Для своей даты ещё два необязательных поля:

- `contact_date` (тип `date` — только день, месяц и год, без времени) — дата, к которой связаться, уже с подставленным годом;
- `contact_date_set_at` (дата и время) — когда эту дату задали; нужно, чтобы засчитывать только заметки после этого момента.

Ограничение в базе (`CHECK`): оба поля заполнены тогда и только тогда, когда `contact_frequency = 'on_date'`. Так в базе не может оказаться «частота раз в месяц, но с датой» или «Другое без даты».

В Drizzle — `pgEnum` и поля в `src/db/schema.ts`. Всё про значения живёт в модуле `src/lib/contacts/frequency.ts`, общем для сервера и браузера: список значений, подписи («Раз в неделю»…, «Другое…»), интервалы, разбор ввода «16.12» и показ «Другое: 16.12».

Почему так, а не иначе:

- Число дней (7, 30, 90, 365) не годится: спека требует календарные месяцы (5 ноября → 5 декабря, 31 января → 28 февраля).
- Обычный текст без ограничения позволил бы записать в базу что угодно; перечисление и `CHECK` отсекают ошибки на уровне базы.
- Хранить «день и месяц» без года и вычислять год при чтении — сложнее и неоднозначно (после 16.12 непонятно, прошла дата или речь о следующем годе). Спека требует, чтобы дата была разовой, поэтому год фиксируется в момент сохранения.

### 2. Срок вычисляется при чтении, а не хранится

Для каждого контакта с частотой считаются два момента — «начало» и «конец срока» — и по ним всё остальное:

- обычная частота: начало — `coalesce(дата последней заметки, contacts.created_at)`, конец — начало плюс интервал PostgreSQL (`'7 days'`, `'1 month'`, `'3 months'`, `'1 year'`). Сложение дат с месяцами в PostgreSQL само переносит 31 января на 28 февраля — как требует спека. Пора связаться, если конец срока раньше текущего момента;
- своя дата: конец — начало дня `contact_date` по часам базы, начало — на год раньше (так превышение считается «как раз в год», по решению владельца). Пора связаться, если конец срока наступил и нет заметки позже `contact_date_set_at`, то есть последняя заметка отсутствует или написана не позже этого момента.

Последняя заметка берётся подзапросом `LEFT JOIN LATERAL (... ORDER BY created_at DESC, id DESC LIMIT 1)` — он идёт по существующему индексу.

Альтернатива — хранить у контакта «следующий срок» и пересчитывать его при каждой заметке и смене частоты. Отказались: два места записи вместо одного, легко рассинхронизировать (например, при откате удаления), а выигрыша в скорости на тысячах контактов нет.

### 3. Одно условие для страницы и для счётчика

Правило живёт в новом модуле `src/lib/contacts/due.ts`: он собирает выражения «начало», «конец срока» и «во сколько раз превышен срок» (через `CASE` по значению частоты) и строит на них запросы:

- список для страницы: `id`, `name`, `about` («кто это»), дата последней заметки и первые 300 символов её текста (`left(body, 300)` — чтобы не тащить в браузер заметки по 10 000 символов);
- число для кнопки на главной;
- есть ли хоть у кого-то частота или своя дата — нужно только для выбора текста пустой страницы.

Во всех трёх — `deleted_at IS NULL` и `contact_frequency IS NOT NULL`, как в остальных запросах.

Порядок: `extract(epoch from now() - начало) / extract(epoch from конец - начало)` по убыванию, затем имя с русской сортировкой (`collate "ru-x-icu"`, как в общем списке), затем `id`.

Функции `due.ts` принимают подключение к базе и текущий момент (по умолчанию `now()` базы) и не зависят от Next.js. В `queries.ts` они обёрнуты как обычно — `listDueContacts()`, `countDueContacts()`, `hasContactsWithFrequency()` с `connection()` и `getDb()`, всегда с `now()`. Параметры нужны, чтобы проверочный скрипт мог выполнить те же запросы с заданным временем («8 ноября в 14:00 / в 16:00», «15 / 16 декабря»), не дожидаясь, — внутри транзакции с откатом, не меняя данных в базе.

### 4. Сохранение — два серверных действия

- `setContactFrequency(contactId, frequency)` — для «Не задано» и четырёх частот. Значение проверяется через zod; вместе с частотой очищаются `contact_date` и `contact_date_set_at`, поэтому своя дата забывается.
- `setContactDate(contactId, prevState, formData)` — для окошка «Другое», в стиле `useActionState`, как форма заметки. Ввод разбирается функцией из `frequency.ts`: одно-два числа, точка, одно-два числа, такая дата бывает (29.02 допустимо). Год подставляет чистая функция «ближайшая такая дата, начиная с сегодня» (29.02 — ближайший високосный год); «сегодня» берётся из базы (`current_date`), чтобы дата считалась по тем же часам, что и сравнение в решении 2. Записываются `contact_frequency = 'on_date'`, `contact_date` и `contact_date_set_at = now()`.

Оба действия обновляют только неудалённый контакт и затем вызывают `revalidatePath("/", "layout")`, как остальные действия. Если контакт не найден — «Контакт не найден: возможно, его удалили»; если база недоступна — общее «Не получилось сохранить…» и запись в лог через `logDbError` (без данных контакта). Неверная дата — «Проверьте дату: день и месяц через точку, например 16.12», введённый текст возвращается в окошко.

Форма «Изменить» (`updateContact`) не трогает новые поля: она записывает только поля из `contactSchema`, поэтому частота и своя дата не сбрасываются.

### 5. Выбор частоты в карточке — выпадающий список и окошко shadcn/ui

Компоненты `select` и `dialog` добавляются в `src/components/ui/` через CLI shadcn, который уже есть в зависимостях проекта. Оба построены на `@base-ui/react` (уже установлена) и не тянут новых пакетов; `dialog` использует уже существующий `button`, его файл CLI менять не должен.

Клиентский компонент `ContactFrequencySelect` в карточке, с подписью «Как часто общаться» и иконкой `CalendarClockIcon`. Он стоит в блоке данных контакта отдельной строкой во всю ширину: под телефоном и почтой, над «Откуда знакомы». Как он работает:

- обычные варианты сохраняются сразу; значение в списке меняется мгновенно (`useOptimistic`), пока идёт сохранение; при ошибке возвращается прежнее значение и под полем появляется сообщение;
- пункт «Другое…» ничего не сохраняет сам, а открывает окошко — при каждом нажатии, даже если «Другое» уже выбрано. У окошка заголовок «Своя дата» и пояснение «Год подставится сам — ближайшая такая дата.», в нём поле «День и месяц» с подсказкой «например, 16.12», заполненное текущей датой, если она задана, и кнопки «Сохранить» и «Отмена». Разделитель — только точка (решение владельца), поэтому поле открывает на телефоне обычную клавиатуру, где точка есть, а не цифровую, где в русской раскладке часто запятая. Успешное сохранение закрывает окошко; ошибка остаётся в окошке; «Отмена» закрывает его, ничего не меняя;
- когда задана своя дата, в списке видно «Другое: 16.12» — день и месяц с ведущими нулями, без года.

Альтернатива для списка — обычный `<select>` браузера: проще, но выглядит иначе, чем остальной интерфейс на shadcn/ui. Ряд из шести кнопок занимает слишком много места на телефоне. Альтернатива для даты — встроенный выбор даты браузера (`<input type="date">`): он требует год и выглядит по-разному в разных браузерах, а владелец хочет вписывать дату вручную в виде 16.12.

### 6. Страница `/keep-in-touch`

`src/app/keep-in-touch/page.tsx`, заголовок вкладки «Пора связаться». Устроена как остальные страницы: ссылка «Все контакты» назад, заголовок, данные внутри `Suspense` со скелетоном загрузки. Строки оформлены как в общем списке (карточка с пунктирными разделителями, аватар `ContactAvatar`), каждая — ссылка на карточку.

- Имя и под ним «кто это» (`about`), если оно заполнено; пустое — без пустой строки.
- На компьютере у списка заголовки колонок «Кто» и «Последняя заметка», как у общего списка; дата и текст заметки — во второй колонке. На телефоне колонок нет: дата и текст идут под именем, с отступом на ширину аватара.

- Дата заметки — новая функция `formatDate` в `src/lib/format.ts`: день, месяц словом и год, без времени («3 сентября 2026»).
- Текст заметки — переносы строк заменяются пробелами, обрезка до двух строк через `line-clamp-2`, многоточие ставит браузер.
- Пустые состояния — в рамке, как `EmptyState` главной, в зависимости от `hasContactsWithFrequency()`: «Со всеми на связи» с иконкой `CircleCheckIcon` или «Частота пока не задана» с подсказкой «Откройте карточку контакта и выберите, как часто хотите общаться.» и иконкой `CalendarClockIcon`. Кнопки «Добавить контакт», как в `EmptyState`, здесь нет.

### 7. Кнопка на главной

В шапке страницы `src/app/page.tsx`, слева от «Добавить контакт», кнопка-ссылка в стиле `outline` с иконкой `ClockIcon` из `lucide-react` (библиотека иконок уже в проекте). Обе кнопки одного размера. На телефоне, где в строку они не помещаются, кнопки стоят друг под другом во всю ширину: ряд кнопок переносится, каждая растягивается. Число получает небольшой серверный компонент внутри `Suspense`; пока оно грузится, показывается та же кнопка без числа — кнопка доступна сразу и не прыгает. Для экранного диктора у кнопки полная подпись: «Пора связаться: 3 контакта».

## Risks / Trade-offs

- [Даты считаются по часам сервера, на сервере это UTC] → около полуночи дата заметки может отличаться на день от московской, календарный месяц прибавляется по UTC, а своя дата наступает в 00:00 по UTC — в 03:00 по Москве. Так же уже сейчас показываются даты в карточке; если это мешает, это отдельная правка часового пояса для всего приложения.
- [Счётчик на главной — лишний запрос к базе при каждом открытии] → запрос лёгкий, идёт по индексу; на тысяче контактов это миллисекунды. Он внутри `Suspense`, так что список контактов не ждёт его.
- [Одновременная смена частоты в двух браузерах] → сохраняется последнее выбранное значение, как и с остальными данными контакта.
- [Выбор частоты не работает без JavaScript] → приложение и так требует JavaScript (поиск, удаление с отменой).
- [Своя дата без года может удивить: 01.03, введённое 5 ноября, — это март следующего года] → так записано в спеке; в карточке видно «Другое: 01.03», а сценарии спеки описывают выбор года.

## Migration Plan

1. `pnpm db:generate --name contacts_contact_frequency` создаёт `drizzle/0002_contacts_contact_frequency.sql`: создание типа `contact_frequency` с пятью значениями, добавление трёх необязательных полей в `contacts` и ограничения `CHECK`. Данные не переписываются: у всех существующих контактов «Не задано», и ограничение для них выполняется.
2. Выкатка как обычно: merge в main → образ → на сервере разовый контейнер применяет миграцию → стартует новый образ → проверка `/health`. Старый образ на время миграции продолжает работать: новые поля ему не мешают.
3. Откат — только вручную, запускает владелец: предыдущий образ работает с новыми полями, отменять миграцию не нужно.
